# V0.4 技术方案：需求预测 + 规则化调度

> 延续 V0.3 的「结构化输出 + 执行器 + 人工确认」模式，把 AI 从异常处理拓展到需求预测与车辆调度。
> 核心边界：**AI 负责预测订单量和给出解释，调度数量由确定性规则计算**，关键动作仍需人工确认。

---

## 一、目标与范围

### 目标

> 从「异常发生后被动处理」升级为「基于历史订单和外部因素，主动预测未来某时段各区域订单量，并给出车辆调度建议」。

典型场景：

```text
今晚 20:00-22:00，CBD 区域
- 历史同期平均订单：120 单
- 外部因素：演唱会
- AI 预测订单：180 单
- 当前可调度车辆：8 辆（每车承载 15 单 → 需 12 辆，缺口 4 辆）
- 规则建议：从 Residential Area 调入 4 辆
- 运营确认后，更新车辆 currentArea
```

### V0.4 做

- 新增「需求预测」页面
- 按区域 + 时段聚合历史订单数据
- 运营输入外部因素标签（天气/活动/节假日）
- AI 生成各区域未来时段订单量预测
- **规则**基于预测 + 当前可调度车辆计算调度建议
- 人工确认后执行车辆区域调动
- 预测与建议落库，为 V0.5 复盘留数据

### V0.4 不做（留 V0.5 或更后）

- 不接真实天气/活动 API（手动标签模拟）
- 不做时序模型/ML（LLM + 规则聚合）
- 不做自动调度闭环（必须人工确认）
- 不做预测准确率实时计算（V0.5 复盘）

## 二、数据模型

### 复用已有表（已核对字段）

| 表 | 用到的字段 |
|---|---|
| `orders` | `area`、`createdTime`、`status`（历史订单聚合） |
| `vehicles` | `currentArea`、`vehicleStatus`（当前分布、可调度数） |
| `daily_forecasts` | 持久化预测结果（现为纯 CRUD，字段够用） |

`daily_forecasts` 是「一区域 + 一时段 = 一行」，字段映射见 §三。

### 新增表 `dispatch_suggestions`

```sql
CREATE TABLE IF NOT EXISTS dispatch_suggestions (
    id BIGINT AUTO_INCREMENT PRIMARY KEY COMMENT '建议 ID',
    forecast_id BIGINT COMMENT '关联 daily_forecasts 行（to_area 的预测行）',
    target_date DATE NOT NULL COMMENT '目标日期（冗余，便于查询）',
    time_range VARCHAR(32) NOT NULL COMMENT '时段，如 20:00-22:00',
    from_area VARCHAR(64) NOT NULL COMMENT '调出区域',
    to_area VARCHAR(64) NOT NULL COMMENT '调入区域',
    vehicle_count INT NOT NULL COMMENT '建议调动车辆数',
    reason TEXT COMMENT '建议理由（规则模板生成）',
    status VARCHAR(32) NOT NULL DEFAULT 'PENDING' COMMENT 'PENDING / EXECUTED / REJECTED',
    confirmed_by VARCHAR(50) COMMENT '操作人，可空',
    executed_result JSON COMMENT '执行结果，如 {movedVehicleIds: [...]}',
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    INDEX idx_forecast_id (forecast_id),
    INDEX idx_status (status),
    INDEX idx_target_date (target_date)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COMMENT = '车辆调度建议记录';
```

**要点**：`forecast_id` 关联的是 **`to_area` 的那条预测行**（是调入区域的需求驱动了这次调度）；`target_date` / `time_range` 是从 forecast 冗余出来的，方便按日期列表查询。

## 三、DTO 设计

### 3.1 前端 → 后端（生成预测的入参）

```java
@Data
public class DemandForecastGenerateRequest {
    private LocalDate targetDate;          // 预测日期
    private String timeRange;              // "20:00-22:00"
    private List<String> areas;            // 预测区域（英文，如 CBD）
    private List<String> externalFactors;  // 外部因素标签，如 ["演唱会", "下雨"]
}
```

### 3.2 后端 → LLM（组装好的上下文）

```java
@Data
public class DemandForecastRequest {
    private LocalDate targetDate;
    private String timeRange;
    private List<String> areas;
    private List<String> externalFactors;
    private Map<String, Integer> historicalAvg;        // area -> 历史同期平均订单
    private Map<String, Integer> currentIdleVehicles;  // area -> 当前可调度(IDLE)车辆数
}
```

> `historicalAvg` 和 `currentIdleVehicles` 由后端聚合/统计后填好，LLM 不查库。

### 3.3 LLM 返回（只返回预测，不含调度）

```java
@Data
public class DemandForecastResult {
    private List<AreaForecast> forecasts;
}

@Data
public class AreaForecast {
    private String area;
    private Integer predictedOrders;
    private String reason;   // 引用历史均值 + 外部因素的解释
}
```

### 3.4 生成接口的响应（落库后返回，带 id）

```java
@Data
public class DemandForecastResponse {
    private LocalDate targetDate;
    private String timeRange;
    private List<DailyForecast> forecasts;          // 已落库的预测行（含 id）
    private List<DispatchSuggestion> suggestions;   // 已落库的调度建议（含 id）
}
```

### 3.5 `AreaForecast` → `daily_forecasts` 字段映射

| AreaForecast | DailyForecast |
|---|---|
| area | area |
| predictedOrders | predictedOrders |
| reason | predictionReason |
| externalFactors（请求层） | weatherSummary（多个标签 join 成字符串） |
| targetDate（请求层） | forecastDate |
| timeRange（请求层） | timeRange |

## 四、AI Provider 扩展

### 4.1 接口

在 `AiModelProvider` 新增：

```java
DemandForecastResult predictDemand(DemandForecastRequest request);
```

`NoopAiModelProvider` 与 V0.3 的 `analyzeIncident` 一样，未启用时抛 `IllegalStateException`。

### 4.2 Prompt 要点（SpringAiModelProvider）

新增独立的 System Prompt（与 Incident 分析分开）：

- 角色：Robotaxi 运营需求预测 Copilot。
- 输入：targetDate、timeRange、areas、externalFactors、historicalAvg、currentIdleVehicles。
- 输出：`forecasts` 列表，每项 `{area, predictedOrders, reason}`。
- 约束：
  1. `predictedOrders` 为非负整数，以 `historicalAvg` 为基准，结合 `externalFactors` 上调/下调。
  2. `reason` 必须引用历史均值与给定的外部因素，不得虚构未提供的外部因素。
  3. 只对 `areas` 里出现的区域输出预测，不得新增区域。
  4. 不输出调度建议（调度由规则计算）。

## 五、调度规则（V0.4 的核心）

调度数量**不由 LLM 决定**，由后端确定性规则计算，公式和算法如下。

### 5.1 配置

`application.yml` 新增：

```yaml
dispatch:
  vehicle-capacity: 15   # 每辆可调度车在每个时段预计承载的订单数
```

### 5.2 算法（纯函数，可单测）

输入：`forecasts`（area → predictedOrders）、`idle`（area → 可调度车辆数）、`capacity`。

```
required[area]  = ceil(predictedOrders[area] / capacity)      # 该区域需求车辆数
deficit[area]   = max(0, required[area] - idle[area])         # 缺口（需调入）
surplus[area]   = max(0, idle[area] - required[area])         # 盈余（可调出）
```

生成建议：

```
for 每个有缺口的区域 D（按缺口降序）：
    while deficit[D] > 0：
        选盈余最大且 != D 的区域 S（盈余相同按区域名升序取稳定解）
        若无 S：跳过（V0.4 不生成"无车可调"类建议）
        n = min(deficit[D], surplus[S])
        生成 DispatchSuggestion(from=S, to=D, vehicleCount=n)
        deficit[D] -= n；surplus[S] -= n
```

### 5.3 reason 模板（规则生成，确定性）

```text
预测 {to_area} 时段 {time_range} 订单 {predictedOrders} 单，按每车 {capacity} 单需 {required} 辆，
当前可调度 {idle} 辆，缺口 {deficit} 辆；从 {from_area}（盈余 {surplus} 辆）调入 {n} 辆。
```

> AI 的"预测理由"在 `AreaForecast.reason` 里；这里的"调度理由"是规则拼装的算术说明，两者各司其职。

## 六、服务与执行器

### 6.1 `DemandForecastService`（编排层，新增）

负责：

1. 聚合 `orders`：近 N 天（默认 30）按 area + 小时段取历史订单均值 → `historicalAvg`。样本稀疏时退化为「同小时均值」，不强求「同星期」。
2. 统计 `vehicles`：`currentArea = area 且 vehicleStatus = IDLE` 的数量 → `currentIdleVehicles`。
3. 组装 `DemandForecastRequest`，调 `aiModelProvider.predictDemand`。
4. 每个 `AreaForecast` 落 `daily_forecasts`（复用 `DailyForecastService.save`）。
5. 调 §5 规则计算 `List<DispatchSuggestion>`，落 `dispatch_suggestions`（status = PENDING）。
6. 返回 `DemandForecastResponse`。

> 注意：预测失败不能拖垮主业务，沿用 V0.3 的降级——`predictDemand` 异常时返回"AI 预测不可用"。

### 6.2 `DispatchSuggestionService`（新增，继承 IService）

复用 V0.3 的状态机模式：

- `confirm(id, confirmedBy)`：CAS `PENDING → CONFIRMED`（原子抢占防重）→ 执行器 → `EXECUTED`，失败回滚到 `PENDING`。
- `reject(id)`：CAS `PENDING → REJECTED`。
- `listByDate(date)` / `listPending()`：查询。

### 6.3 `DispatchSuggestionExecutor`（新增）

确认后执行：

1. 校验 `status == PENDING`（由 service 的 CAS 保证）。
2. 从 `from_area` 查 `vehicleCount` 辆 `vehicleStatus = IDLE` 的车（新增 `VehicleService.listIdleByArea(String area)`）。
3. 若可调度车辆不足 → `BusinessException(409, "调出区域可调度车辆不足")`。
4. 逐辆更新 `currentArea = to_area`。
5. `executed_result = { movedVehicleIds: [...], count: n }`。

> 与 V0.3 相同：单事务，业务失败整体回滚到 `PENDING`，不落 `EXECUTION_FAILED` 死状态。

## 七、接口清单

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/demand-forecasts/generate` | 生成预测 + 调度建议（落库） |
| GET | `/api/demand-forecasts` | 查询历史预测（可选 `date` 参数） |

> 既有 `/api/daily-forecasts` CRUD 保留不动；新的编排走 `DemandForecastController`，持久化仍复用 `DailyForecast` 实体，避免两套"预测"概念打架。

## 八、前端

新增页面「需求预测」（路由 `/dispatch-forecast`），左侧菜单加入口。

1. **条件区**：日期选择、时段下拉（固定几档）、区域多选、外部因素标签输入。
2. **预测结果区**：各区域预测订单卡片（预测订单 vs 当前可调度车辆，理由折叠展示）。
3. **调度建议区**：建议卡片（「从 A 调 B 辆到 C」+ 理由），确认 / 拒绝按钮（复用 V0.3 卡片模式），确认后刷新车辆列表与预测列表。

区域用现有英文值展示时经 `AREA_LABEL` 映射中文。

## 十、验证

- **规则单测**：固定 forecasts/idle/capacity，断言生成的建议列表（数量、来源、去向）——这是 V0.4 最值得测的纯逻辑。
- **手动验证**（复用 V0.3 方式）：插入一条 PENDING `dispatch_suggestions` → 调 confirm → 查 `EXECUTED` + `executed_result.movedVehicleIds` + 对应车辆 `currentArea` 已变。
- **端到端**：生成预测 → 看预测卡片 → 确认调度 → 车辆列表 `currentArea` 刷新。
